# using-daynight Goal 工作流需求

状态：已采用的设计，skill 实施待交付。当前公开行为仍由
[Agent skill 需求](daynight-agent-skill.md)拥有；本文定义其 Goal 扩展的目标行为，
[架构设计](../design/daynight-goal-workflow.md)拥有机制，
[任务拆分](../design/daynight-goal-workflow-tasks.md)拥有交付范围与任务身份。

## 目的与范围

需要多个独立、可持续追踪的交付步骤才能完成的工作，应先把整个问题说清楚，再完成
架构设计与持久任务拆分，最后按依赖实施。Goal 指这样的任务链，使用现有 task、
`dependsOn`、附件和 PR 属性表达，不增加服务端资源、数据库字段、任务状态、CLI
命令或 skill 模式。一次实现中的命令、测试和临时执行步骤不需要机械拆成持久任务；
一个独立交付成果仍使用普通任务。

本扩展适用于仓库内随 npm 发布的 `using-daynight` skill，不修改已安装的 skill 副本。
现有四种模式、项目发现、精确版本、任务与附件错误语义、安装、并发和交付授权规则继续
有效。本文没有产品 UI 变更；对未来 UI Goal 的原型要求是工作流的一部分。

## 必须交付的行为

| 编号 | 要求 |
|---|---|
| GW1 | `create-task` 在已有创建许可内，根据工作是否包含多个独立交付阶段选择普通任务或 Goal；用户无需使用特定关键词。复用已有任务前读取完整问题、范围、附件和验收目标，不能仅按标题判断身份。 |
| GW2 | 登记 Goal 时同时创建或复用 `[Goal]<outcome>` 和 `Architecture design and task breakdown: <outcome>` 两个起始任务；后者通过 `dependsOn` 依赖前者。每个任务都有描述问题与真实引用的正文，以及包含“方案”和“验收标准”的主 Markdown 附件。 |
| GW3 | 起始附件定义当前阶段要做什么和何时完成。完整 Goal、架构、任务拆分及 UI 原型分别是相应阶段的产出，不能成为启动其生产阶段的前提。两个起始任务及各自阶段资料确认可读后，`create-task` 返回，不开始执行。 |
| GW4 | Goal description 明确整个问题、背景、最终结果、范围、必要行为与约束、明确排除项、可观察的整体验收条件和验证方法。此阶段不修改生产实现代码，也不作架构决策。 |
| GW5 | 涉及 UI 的 Goal description 明确最终外观、交互和代表性数据，产出最终视觉样式、可纯前端交互的 mock UI 及必要资源。覆盖相关的有数据、空、加载、失败、禁用、长内容与窄屏状态；不适用的状态可说明原因。允许原型文件代码，不能用简化样式或静态草图代替交互原型。 |
| GW6 | Goal description 的完整要求、适用原型与本阶段验收经核验清楚，并完成仓库要求的必要交付后，该任务可以设为 `done`。这只完成问题定义，不能据此宣称整个 Goal 完成。 |
| GW7 | 后继设计任务以已完成的 Goal 为输入，完成架构、职责、关键决策与边界契约，并实际登记覆盖完整目标的持久交付任务，不能只交付待建清单。每个交付任务包含问题、范围、方案、验收条件、验证方法与真实资料引用，并可追溯 Goal 和设计。实际前置关系只由 `dependsOn` 表达；没有其他实施前置任务的交付根任务依赖设计任务。 |
| GW8 | 设计任务遵守目标仓库的文档、独立审查和 PR 要求。需要设计 PR 时必须创建 PR，保存完整 PR 属性；所有必要 PR 经平台确认合并且阶段验收满足前保持 `in_progress`。交付任务在设计完成前保持依赖阻塞，设计阶段可以登记它们，不执行它们。 |
| GW9 | 资料要求按阶段判断：澄清需要阶段 brief；设计需要已完成的 Goal 及其适用原型；实施需要已完成设计及自身方案、验收、适用原型和资源。缺失必需输入或依赖未完成时保留实际状态与具体问题，不能凭标题补出方案，也不能跳过阶段解锁后继。 |
| GW10 | 明确许可创建某个 Goal 覆盖其两个起始任务和目标范围内的后续拆分登记，无需逐项重复取得许可。不包含无关任务、实现、发布、部署、外部通信、PR 合并或主线 push 权限；已有明确授权继续按其范围生效。仅有实现或 autopilot 权限不能推导创建许可。 |
| GW11 | 创建、依赖、附件与引用写入都要读回核验。部分成功保留已确认 task ID，完成未完成的登记；不确定写入先核对实际结果，不能重复创建任务链。使用决策时读取的精确版本，保留完整字段、有效引用和真实错误。不存在原子 Goal 创建、锁或独占 claim。 |
| GW12 | `run-task` 只执行指定 ID，完成或需要外部介入时返回；创建 Goal、完成描述或完成设计都不自动启动 autopilot。只有明确启动的 autopilot 才能在当前任务确认 `done` 后选择下一相关任务；CI、review、合并等待仍属于当前任务。 |
| GW13 | 整个 Goal 只有在全部交付任务确认完成、必要 PR 平台确认合并，并且原始完整 Goal 的整体验收满足后才完成。空 ready 页、描述完成、设计完成或单个实施 PR 创建都不足以证明完成；部分结果和阻塞必须准确报告。 |

## 资料与完成证据

task `description` 保留当前任务的问题和真实附件引用；一个主 Markdown 附件拥有该阶段
的方案与验收。完整 Goal 要求由描述任务的主附件拥有，设计由设计任务的主附件拥有；
仓库文档可以拥有完整规范与设计，但附件仍须让执行者独立理解工作和验收。不得把依赖
清单、方案、验收或执行流水放入 task 描述以绕过资料要求。

UI 原型在描述阶段完成后供设计与相关交付任务复用，引用必须指向实际可读资源。验收
结果与必要交付证据写入相应主附件的验收项；需要 PR 时保留 merge commit 引用。
当前任务、阻塞、等待事项和下一步使用会话或项目已有检查点，不增加专用服务字段。

开发任务及通过 PR 交付的设计、文档任务继续遵守当前 skill 的完成规则。用户要求保留
PR 供审阅时，任务保持 `in_progress` 并返回等待；完成要求不授予合并权限。没有 PR
交付路径的澄清任务按其明确阶段验收完成。

## 验收与证据边界

| 检查 | 必须观察到的结果 |
|---|---|
| 情境审查 | 独立审查普通单任务、多交付阶段、UI 澄清、两个起始任务、已有链复用、缺少许可、范围内拆分、部分写入、精确版本冲突、设计 PR 等待、单任务返回和整体验收；无未处理的 Critical/Major。 |
| 静态资料 | 入口 frontmatter、四份模式引用及共享 Goal 协议、所有本地链接、英文发布内容、阶段要求与授权一致；相关 active 文档及决策路径同步。 |
| 构建与打包 | 既有资源复制与链接检查及实际 build、npm pack 证明完整新协议随包发布，复制后文件与源码一致，已有安装覆盖与 scope 规则继续有效。 |
| 工具门禁 | 按实际改动执行 CLI typecheck、test、build 和所需 CI；文档检查包括新增文件、链接、note 格式与 `git diff --check`。 |

情境审查检验指令的含义与阶段是否可执行，不证明任意模型必然遵循。复制和安装证据
证明资源与文件操作，不证明任务已经执行。该扩展不增加运行时模型或后台调度，因此
无需新增 telemetry、数据库迁移或服务验收；已有任务和附件命令继续由原有套件验证。
