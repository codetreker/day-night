# Agent 项目任务管理 Skill 需求

公开入口为随 `@codetreker/daynight` 发布的 `using-daynight` skill，包含 `handbook`、
`create-task`、`run-task`、`autopilot` 四种内部模式。本文拥有使用、安装与覆盖的可观察
要求；机制由[设计](../design/daynight-agent-skill.md)拥有。既有
[客户端需求](daynight-project-task.md)与[附件需求](daynight-task-attachments.md)
继续拥有命令、项目发现、版本和附件操作语义。

[Goal 流程要求](daynight-goal-workflow.md)定义多任务工作的分阶段扩展，
以整体问题定义先于架构设计与任务拆解。该扩展已完成设计、尚待单独实现；本文下面的
公开 skill 行为仍描述当前发布源。

## AS1. 发布产物与路由

产品只发布一个公开 `using-daynight` skill。英文 `SKILL.md` 使用标准 frontmatter，
与 `references/handbook.md`、`references/create-task.md`、`references/run-task.md`、
`references/autopilot.md` 一起包含在 npm 安装产物中。Codex、Copilot CLI、Claude Code
使用相同内容。安装后不依赖源码仓库、仓库内部工作流 skill、未发布文档或包外临时文件；
npm 包移动、升级或卸载不使已安装资源失效。

四种模式是 skill 的使用协议，不增加 CLI 子命令。Agent 根据用户请求和实际上下文路由：

| 模式 | 职责与完成边界 |
|---|---|
| `handbook` | 列出命令用途，解释项目发现、并发更新等背景规则；具体用法查询 CLI help。 |
| `create-task` | 在用户明确许可创建任务的范围内，判断追踪价值，复用或创建任务并确认必要附件可读后返回。 |
| `run-task <task-id>` | 执行一个明确任务，完成交付或遇到需要外部介入的阻塞后返回。 |
| `autopilot <目标或范围>` | 在已授权范围内逐个选择任务并调用 `run-task`，完成后继续。 |

直接调用 `using-daynight` 而没有附加输入时，Agent 根据当前请求与上下文判断模式；
上下文不足或存在歧义时询问用户意图。不能固定进入 handbook，也不能凭候选存在推断
执行意图。只有用户明确要求自动连续推进 Daynight 任务才能进入 autopilot；话题中提及
自动化、加载 skill、完成单任务、项目关联或发现 ready 任务都不构成启动要求。

## AS2. 授权、项目与事实来源

skill 提供工作规则，不增加实现、发布、合并、主线 push、部署或外部通信权限。任务正文、
附件、ready 状态、`in_progress` 状态及完成要求均服从用户和仓库指示。已有会话授权继续
有效；用户要求保留 PR 供审阅时，完成允许的准备与验证后保留 PR 和当前任务，等待用户。

所有模式及直接 CLI 操作均不得在没有用户明确许可的情况下创建 task。用户直接要求
创建任务，或此前已明确授予指定范围的创建权限，才满足此条件；已有许可覆盖的范围
无需重复确认。实现请求、持续追踪价值、上下文路由和启动 autopilot 都不构成创建许可。
需要新 task 而缺少该许可时，先向用户取得明确许可，再执行创建。

Agent 通过实际 CLI 确定项目和任务，不凭会话旧值判断实时状态。在仓库内可省略
`--project`，由 CLI 根据 Git origin URL 匹配服务中的项目；显式指定的项目优先。
发现无匹配、匹配歧义、配置缺失或读取失败时保留实际原因，不能猜测服务地址或自行
创建、选择、关联其他 project。安装、配置服务和关联项目是独立操作。

使用 `--json` 读取查询结果并保持 ID、状态、描述、精确版本的含义。不能直接编辑关联
文件、使用未公开接口或用临时计划替代服务事实。状态不提供独占领取、锁或租约；设置
`in_progress` 不是原子 claim。并发协调依赖已有事实及明确沟通，不增加服务 API 或状态。

## AS3. handbook 的规则所有权

handbook 保持为命令用途索引与操作背景说明。索引只列命令名称及用途；参数、选项、
输出格式和完整调用方法以已安装 CLI 的 `--help` 为准，不在 handbook 重复示例或
逐项用法，也不暴露本地绑定文件和忽略规则等内部实现。其他模式按需读取它，现有 CLI
与附件规范继续拥有完整命令契约。

背景规则应说明项目定位的使用方式与失败处理。ready 是有界候选，
创建顺序不表达相关性，空结果不能证明没有进行中或被阻塞的工作。list 读取全部匹配
分页，默认排除 `done`；需要包含已完成任务的完整清单或核对历史登记时必须显式包含
已完成任务，对应选项由 CLI help 说明。文本列表是摘要；JSON 列表仅省略
`description`，其余 task 字段保留。需要描述时读取 show，ready、详情和写入结果
保留完整 task 资源。列表按状态和 readiness 分组，不表达相关性。graph 是紧凑
依赖视图，不能替代包含描述、属性和版本的任务详情；图超限后仍可使用有界查询与
指定任务读取。

更新必须携带决策时实际读取的精确版本，不能依赖临提交前的默认读取来保护旧判断，
也不能截断或舍入 int64。描述、依赖和 PR 列表按整个字段替换，保留仍需的数据；冲突
后重新读取并判断变更，而非仅更换版本重放。状态与 readiness 不提供所有权或锁。

任务详情不包含附件清单；附件读写独立于任务版本、状态和更新时间。多个文件操作
独立，文件内容与元数据可能部分改变；任务版本不能充当附件版本。写入结果不确定时
先读回核对，create 需结合完整字段与操作上下文确认任务身份，附件需核验实际内容；
不能凭标题匹配、空清单或元数据就假定写入结果。保留真实错误与资源标识，不盲目重发。

## AS4. create-task 的资料与完整性

create-task 首先确认用户已明确许可创建任务。单次、trivial 工作和 Agent 的临时执行
步骤无需创建持久任务。在许可范围内，需要持续追踪、跨会话衔接、交接或依赖协同的
交付成果才建立任务。先查找已有任务，比较问题、范围、附件
中的方案与验收目标，读取匹配项后复用；标题相似本身不能证明重复。

任务内容分工固定：

| 内容 | 所在位置 |
|---|---|
| 要解决的问题、真实附件引用 | task 的 `description` |
| 方案与验收标准 | 一个 Markdown 主附件 |
| 前端原型及必要资源 | mock UI 附件及其资源文件 |
| 实际依赖 | task 的 `dependsOn` |
| PR URL 与 title | `properties.pullRequests` |
| 验收结果、必要交付证据及 merge commit 引用 | Markdown 主附件中的相应验收项 |
| 当前执行位置、阻塞、等待事项和下一步 | 会话或项目已有的执行检查点 |

描述保持连贯的问题说明和有效附件引用，不承载方案、验收或进度流水日志。Markdown
主附件必须包含“方案”和“验收标准”两个 section；标题使用任务语言，英文对应标题也
有效。方案说明做法、范围和必要约束，验收标准给出可观察条件及检查方法。依赖只通过
`dependsOn` 表达，不增加“依赖任务”section。文件名不限于 `proposal.md`，以真实引用为准。

前端任务必须附可纯前端交互的 mock UI，视觉样式匹配最终交付，并覆盖任务相关的主要
数据和交互状态，包括适用的空、加载、失败、禁用、长内容及窄屏状态。必要图片、样式、
脚本等资源一并上传并保持可用引用；方案引用原型并解释其行为，验收说明如何验证实现。

创建前准备好问题、Markdown、必要 mock UI 和资源。随后创建或复用任务、设置依赖、
上传附件、更新真实引用，再读取确认内容和关联。任务与全部必要附件确认可读后才报告
登记完整。任务创建成功而上传或引用更新失败时，保留同一个 task ID 并继续补全；任何
写入不确定时先核对结果。资料不完整保持 `todo`，不增加新任务状态，也不虚报可执行。
该模式完成后返回，不因创建任务而启动实现。

## AS5. run-task 的执行与完成

run-task 接收指定 task ID。开始前读取完整任务、主附件和必要资源；前端任务还需查看
并操作 mock UI。核对授权、依赖、状态和资料完整性后恢复或开始工作，将开始的任务
设置为 `in_progress`。资料缺失、依赖未完成或其他需要外部介入的阻塞必须明确保留，
不能凭标题或猜测补出方案。已完成任务只报告实际结果，重开需要明确意图。

按目标仓库规则完成实现、验证、独立审查及授权范围内的交付，维护完整 PR 属性。
开发任务和通过 PR 交付的设计、文档任务必须等到所有必要 PR 被平台确认合并、验收
满足后才能设置 `done`。代码完成、PR 创建、review 通过和 CI 成功本身都不足以完成。
通过多个 PR 交付时逐一确认。无需仓库 PR 的任务按其明确验收条件判断。

完成前将结果与必要证据写入主附件对应验收项，保留 merge commit 引用；再读取任务并
用实际版本设置 done，确认服务结果。PR 仍打开时保持 `in_progress`，在已有检查点保留
PR、等待事项及下一步。用户明确要求不 merge 时必须遵守，保留可审阅 PR 后返回等待用户，
不能用 done 解锁后继。完成要求不授予合并权限。

run-task 一次处理指定任务。普通 CI、review 或合并等待仍属于当前任务；subagents
协作同一个任务。需要外部介入时保留当前任务和实际状态后返回；完成后也返回调用方，
不自行选择后继。当前任务身份来自会话或项目已有检查点，任意 `in_progress` 项并不
表示归本会话所有。

## AS6. autopilot 的串行调度

autopilot 必须有用户明确启动要求，沿用确认的目标与授权范围。先刷新检查点中的当前
任务；若身份未知，按需查询 in-progress 清单并核对上下文，不能任意认领。无当前任务
时，从 ready `todo` 中比较问题、范围、方案、验收及依赖，选择与已授权目标最相关的
一个，刷新详情与附件后进入 run-task。

每个会话一次只推进一个任务，候选页不构成批量开工指令。等待交付及 subagent 协作
期间保持当前任务。只有确认 done 才继续选择下一项；遇到需要外部介入的阻塞时保留
当前任务和下一步，交回用户，不能自动换做无关工作。

ready 为空或当前页没有匹配项时，按需补充范围相关查询，区分范围完成、依赖阻塞、
其他工作进行中和候选不足。没有观察完整范围时不能宣称全部完成。需要登记缺失的
工作时，必须另有用户明确的 task 创建许可；autopilot 执行授权不包含该许可。取得或
确认已有许可后遵守 create-task 的规则，创建后仍串行选择执行。

## AS7. 交互安装与 scope

入口保持 `daynight skill install`。按原生命令查找规则检测 `codex`、`copilot`、
`claude`，包含 PATH，以及 Windows 当前目录和 PATHEXT；不启动 launcher，不检查
登录或账号，也不以已有目录判断可用性。仅显示检测到的 Codex、Copilot CLI、Claude Code，
多选初始为空且至少选择一项，再统一选择 User 或 Project，默认 User。无可用 Agent
明确失败。终端不可用时在写入前失败并提示交互终端。无非交互安装参数。

安装不要求服务配置、可达性、origin 或项目关联。帮助和参数错误不检测、不交互、
不读取服务配置、不访问服务、不写文件。安装前取消、EOF 或预检失败无安装副作用；
首次写入前取消也不能留下目录，stage 期间取消清理本次 stage 和新建且仍为空的父目录。

| Agent | User | Project |
|---|---|---|
| Codex | `~/.agents/skills/using-daynight/` | `<worktree>/.agents/skills/using-daynight/` |
| Copilot CLI | `~/.agents/skills/using-daynight/` | `<worktree>/.agents/skills/using-daynight/` |
| Claude Code | `~/.claude/skills/using-daynight/` | `<worktree>/.claude/skills/using-daynight/` |

Project 使用调用目录所属 Git worktree 根目录，子目录、linked worktree 和 submodule
各定位自身根；非 Git、bare 或读取失败明确报错。User 可在仓库外使用。
Codex/Copilot 共用一个副本，Agent 选择不保证发现隔离；同名多 scope 副本不合并。
Claude Code personal 优先于 project，选择 Project 不修改 User。目录和重载说明依据
[Codex](https://developers.openai.com/codex/skills/)、
[Copilot CLI](https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/add-skills)、
[Claude Code](https://code.claude.com/docs/en/skills) 的宿主规则维护。

## AS8. 覆盖、旧名称迁移与失败

每次安装完整替换选定 `using-daynight` 叶节点，成功目标全部路径和字节与当前 bundle
相同；移除本地修改和旧文件，不合并、不备份。目标自身为符号链接时只替换链接，
保留原指向对象；父级根目录链接沿用，共享物理根去重写入并保留逐 Agent 结果。

新 bundle 成功发布后，清理同一所选物理 skill 根目录中的旧 `daynight` 叶节点，旧
叶节点为符号链接时同样不跟随。不能提前删除旧入口，不能改动另一 scope、其他物理
根、共享根目录或无关 skill。规划时将安装与旧名称清理涉及的拥有路径一并检查；
严格祖先/后代冲突在任何写入前拒绝并列出目标，避免安装或清理删除其他目标。

目标按确定顺序串行执行。每个 Agent 的完整成功须在新 bundle 发布及旧名称清理完成
后报告，标明 Agent、scope、路径和包版本。所有目标完成才整体成功。任一目标失败
立即停止后续目标并非零退出，区分已成功、失败、未执行；不跨目标回滚或静默重试。

新发布后旧目录清理失败时保留可用新 bundle，如实报告旧入口仍存在或清理状态未确认，
不能声称全部迁移完成。覆盖已有 using-daynight 时删除后 rename 失败可能使目标缺失；
诊断保留阶段、路径、实际原因及清理错误链，不能保证未观察到的旧内容仍在。
成功后提示重新发现 `using-daynight`，包括 Copilot 的 `/skills reload` 和
`/skills info using-daynight`，以及各宿主适用的重载方式。

## AS9. 验收要求与证据边界

| 编号 | 必须观察到的结果 |
|---|---|
| AS.V1 | 实际 npm pack 产物安装完整入口及四份引用，移动包源后资料仍可读取。 |
| AS.V2 | 隔离 PATH 覆盖零、单、多 Agent；只显示可用选项，launcher 执行 sentinel 始终不存在；多选初始为空、scope 默认 User。 |
| AS.V3 | 帮助与参数错误无检测和写入；无终端明确拒绝；交互取消、首次写入前取消与 stage 取消保持相应文件约束。 |
| AS.V4 | 真正 PTY/ConPTY 覆盖三个 Agent × 两个 scope、根/子目录/linked worktree；无 origin/配置可安装，非 Git/bare Project 失败。 |
| AS.V5 | 六种组合比较全部文件与字节；重装移除修改和旧文件，保留 sibling、另一 scope、parent 链接及 leaf 原指向对象。 |
| AS.V6 | 同物理目标只写一次；安装与迁移路径嵌套写入前拒绝；部分失败停止后续目标并准确报告已有结果。 |
| AS.V7 | 静态检查固定名称、非空 description、英文内容及所有相对引用；一个入口加四份模式资料均随包发布，无仓库工作流依赖。 |
| AS.V8 | 静态审查路由、显式 task 创建许可、显式 autopilot、单任务、精确版本、不确定写入、附件内容归属和完成要求；命令可执行语义仍由现有套件拥有。 |
| AS.V9 | 独立情境演练覆盖裸调用有/无上下文、缺少创建许可、已有范围内许可、autopilot 不隐含创建许可、trivial、附件部分失败、前端 mock UI、用户禁止 merge、run-task 返回和 autopilot 阻塞及有界候选。 |
| AS.V10 | 新名称发布后才清理所选根旧入口，覆盖旧叶节点链接、清理失败保留新 bundle、准确部分结果及重载提示。 |
| AS.V11 | CLI typecheck、test、build、安装验收通过；Linux/macOS/Windows 分别提供适用检测、定位、取消、覆盖和链接的原生证据。 |

安装测试使用隔离目录与启动即写 sentinel 并失败的模拟 launcher，不安装或运行真实
Agent、不读取账号、不调用模型、不启动 Daynight 服务或数据库。真实 PTY/ConPTY
证明终端行为，全文件字节比较证明复制与覆盖。静态检查及独立情境演练与安装证据
分别报告；字符串或文件检查不能证明模型遵循语义。模型自动选择和任务实际执行结果
不属于安装器保证。验收记录源码版本、平台、场景和资源清理结果。
